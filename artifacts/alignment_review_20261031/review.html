ResolveGuard implementation alignment and next steps

Reviewed October 31, 2026. Scope: the local learning/demo application, its original PRD v0.4 and Observability BRD, subsequent customer-chat/admin specifications, implementation code and recorded evaluation results.

ResolveGuard largely follows the agreed demo direction: customers can ask public questions, identify the right product, securely enter a simulated account journey, report a problem and receive a verified receipt. It is partly aligned with the full design, not feature complete or ready for real banking customers. The main remaining work is answer verification, complete evaluation coverage, useful reviewer workflows and authoritative operational integrations.

No customer-facing code, banking data, credentials or running configuration was changed during this review. The original product PDFs and workbook are preserved.

How the conclusion was reached

An item counts as working when implementation and relevant test evidence exist. An item is partial when only part of its promised behavior works. A specification, schema, installed library or configured key alone does not establish a working integration. A small pilot does not establish broad quality or production safety.

The original PRD favors one customer-facing assistant with controlled specialist services. That matches the current direction. Resolution and QA are mostly Python rules and evidence checks; they are not three independently reasoning AI models. The original PRD preserves older 60-case material and appends the v0.4 controls for 100 original RG cases. The additional 100 BOW cases are a separate dataset. Neither 100-case requirement is satisfied by running the selected 40 cases.

The current customer journey

Message → Security and intent checks → Public policy, permitted lookup, or report intake → Verified next steps → Reply checks → Customer response → Session audit

Public questions use a direct web-service path; account conversations use LangGraph, the framework that controls the order of workflow steps. Both pass through the shared response checker. The diagram describes responsibilities, not a claim that every box is a separate LangGraph agent or AI call.

Important findings

Answer verification needs strengthening before live generated replies

An isolated check changed a BOW fee answer to an incorrect fictional $999 fee while keeping its original valid policy sources. The current gate returned APPROVE, including GROUNDING=PASS. The test used temporary storage and did not change a customer session.

This establishes a specific gap: checking that a source is genuine does not check that the answer correctly uses it. The current controlled templates reduce the immediate exposure, but the gate must not be relied on as a complete defense for a future freely generated answer. Similar independent checks are needed for unsupported amounts, waiver conditions, product mix-ups and promises of action.

Recommended completion test: a changed fee, rate, condition, case state or promise is rejected even when valid sources are attached. A failed source/receipt check must continue to fail closed. Use deterministic checks for exact financial facts; add calibrated semantic assessment where rules alone are insufficient.

The review queue currently marks every audited session for review

The local snapshot contained 22 completed audit jobs, all with NEEDS_REVIEW. The code intentionally marks online intent accuracy NOT_EVALUABLE, since no independent reference label exists, and then treats any non-pass finding as a reason for post-session review. The jobs completed technically; this does not mean a human reviewed them or a customer problem was resolved.

Recommended completion test: a session with no detected safety issue, an unmeasured quality dimension and a confirmed safety failure remain distinct. Unknown quality must stay visible without making every session equally urgent. Create ownership, review status and completion actions without downgrading critical failures.

Resolution records next steps but cannot promise operational outcomes

The service records a verified report/case/handoff reference when its implemented paths apply. It has no authoritative priority assignment or callback service. Its unresolved triggers are limited; it is not a comprehensive assessment of every unfinished conversation. A normal saved-case confirmation is not, by itself, a full case-resolution decision.

Recommended completion test: every agreed unresolved journey records an owner, supported next action and either a verified callback commitment or an explicit unconfirmed state. Do not introduce arbitrary promised response times.

Review evidence is spread across separate stores

Banking events, conversation checkpoints, public turns, workflow traces, security events and QA reports exist, but the operations dashboard does not join them into one customer-session history. Security event records do not currently expose a shared session/turn reference for straightforward reviewer navigation.

Recommended completion test: an authorized reviewer can follow one session from the customer request through product choice, access decision, policy evidence, tool result, delivered reply and review outcome. Playback must not repeat banking actions. Exact displayed response retention needs its own privacy controls.

Full qualification remains blocked

The latest versioned 40-case run passed 39 cases. Its remaining failure is the previously known policy-evidence failure, RG-056. Both intent accuracy and fraud/error recall were 100% within this mock development set. These percentages do not establish live model quality.

The original RG-001 through RG-100 release suite has not been fully executed by this runner. The separate 100 imported BOW cases remain NOT_RUN. Human review, prompt provenance and independent judge calibration are still pending.

The security change preserved the original 40-case file. A versioned copy changes only RG-054's superseded routing/state expectation to the newly requested attack block, with additional flag and no-restricted-call assertions. Its labels still require human review. Results before and after that label change must not be presented as a pure improvement in model quality.

Recommended implementation order

Order Next work Why it comes next Completion evidence
1 Strengthen answer verification and fix RG-056 retrieval Close known truthfulness gaps before adding free-form model replies. Wrong facts with valid citations are blocked; the unchanged failure reproduces and then passes with the right policy.
2 Make post-session review useful Prevent an undifferentiated queue from hiding real problems. Normal, unknown-quality and critical-failure sessions are distinguishable; review ownership and completion are recorded.
3 Agree and human-review the evaluation baseline Ensure the tests describe intended behavior. Keep original RG and BOW suites separate; approve label revisions and expected outcomes with provenance.
4 Execute the original 100 risk cases and the 100 BOW cases Measure actual coverage instead of equating imports with tests. Every case has a result or explicit block; all designated critical assertions pass. Add adversarial and multi-turn regression coverage.
5 Join evidence and add the read-only reviewer workspace Make failures explainable and actionable. Staff-scoped search, one-session timeline, source/tool evidence, notes and safe playback. Connect optional aggregate monitoring across public and private routes.
6 Broaden semantic evaluation and verify LangSmith Measure answer quality and hosted trace delivery separately. Human-reviewed references, calibrated judge agreement, verified cloud read-back and documented minimal outbound fields. Cloud verification needs the key.
7 Add authoritative priority, callback and approved contact services Give supported commitments rather than invented wait times. Backend-assigned priority, accountable queue and verified callback/fallback events.
8 Consider live chat model and hosted deployment Increase complexity only after the checks and evidence work. Controlled pilot, cost/latency results, failure fallback, rollback and explicit data/privacy decisions.

Orders 1 and 2 can be completed locally without cloud credentials. Several later steps can progress in parallel once their own prerequisites are satisfied. Adding vector search, voice, long-term agent memory or more independent AI agents is not necessary for these next steps.

Product decisions still needed

Agree the demo acceptance scope and the authoritative test-suite versions. Assign who approves sample policies and evaluation answers, who owns urgent incidents, and which queues/contact channels the app may display. Define retention for original reports versus minimized review evidence. Before real customers, select the actual identity/case/banking services and approve privacy, service targets, incident response and rollout gates. Do not invent business success baselines.

For the learning demo, missing real banking services should stay explicitly simulated. For production, they become prerequisites; they are not small UI tasks.
